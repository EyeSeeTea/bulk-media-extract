## Context

The current wizard flow asks users to configure storage before they can verify the concrete output generated by their template. Existing preview behavior is optimized for quick sample feedback, not for a pre-export validation pass over every selected file. This change shifts preview earlier in the flow and expands it into a validation checkpoint that can prevent invalid exports before storage settings are entered.

## Goals / Non-Goals

**Goals:**
- Move preview ahead of storage in the wizard without losing existing step-state persistence.
- Build a preview dataset that resolves every exportable file into a row containing source file details, computed destination path, and size.
- Detect duplicate computed destination paths and surface them as blocking errors in the preview step.
- Show aggregate preview statistics so users can assess export volume before proceeding.
- Render an export-configuration button in the preview step as a placeholder for future configuration export work.

**Non-Goals:**
- Generating or downloading a migration/export configuration file.
- Changing storage provider configuration behavior beyond moving it later in the step order.
- Introducing backend processing or new external integrations for preview generation.

## Decisions

### Keep preview as a wizard step, not a side panel
The preview remains a first-class step in the existing wizard sequence rather than being embedded into the template builder or storage step. This keeps validation gates aligned with the existing step-navigation model and avoids splitting blocking feedback across multiple screens.

Alternative considered: keep storage before preview and add an inline preview panel. Rejected because it preserves the current sequencing problem and weakens the notion of preview as a gate before continuing.

### Build preview rows from selected-file export units
Preview data will be computed at the file level rather than at the event-sample level. Each selected file dataValue that matches the current scope becomes one preview row with the resolved target path and size metadata, allowing the UI to represent the exact export set.

Alternative considered: continue using event samples and derive counts heuristically. Rejected because duplicate-path detection and total-size reporting require the full export set, not a bounded sample.

### Treat duplicate destination paths as preview validation errors
Duplicate resolved target paths will be computed in the preview preparation layer and returned as row-level markers plus an aggregate error state. The wizard step will use that error state to block navigation to storage and display guidance to revise the template.

Alternative considered: detect duplicates only in the UI after rendering rows. Rejected because validation logic would become presentation-specific and harder to reuse in tests.

### Add a visible placeholder action for export configuration
The preview UI will render an Export configuration button now, but the action will remain non-functional or explicitly not yet implemented. This reserves space in the interaction model without implying that export packaging is available in this change.

Alternative considered: omit the button until generation exists. Rejected because the requested workflow needs the action exposed now to anchor future follow-up work.

## Risks / Trade-offs

- [Large preview datasets increase browser work] -> Mitigation: keep preview computation in the existing async flow and render rows with predictable tabular structure; implementation can add pagination or virtualization later if needed.
- [Fetching all matching files may be slower than the current sample preview] -> Mitigation: scope the preview to already selected filters and communicate loading/progress clearly in the step UI.
- [Destination path uniqueness rules may be sensitive to normalization details] -> Mitigation: define duplicate checks against the exact resolved target filepath string used for export execution.
- [Placeholder button may confuse users if it appears actionable] -> Mitigation: label or handle it clearly as unavailable for now rather than silently doing nothing.
